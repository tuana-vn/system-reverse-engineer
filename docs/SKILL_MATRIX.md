# Skill Matrix — System Reverse Engineer 4.0

This matrix is generated from the skills actually present in 4.0 and maps them to 4.0 use cases/workflows.
A skill is reusable methodology; prefer the workflow column when a controlled use case exists.

| Skill | Category | Primary Use Case(s) | Preferred Workflow | Purpose |
|---|---|---|---|---|
| `adversarial-baseline-audit` | Evidence Gate | UC-01/10 | `full-reverse-engineering / architecture-drift-rebaseline` | Challenge promoted reverse-engineering baseline claims by trying to disprove them, detect over-generalization, stale evidence, test-as-runtime mistakes, and persistent hallucination before high-impact migration or design work. |
| `architecture-drift-detection` | Baseline Maintenance | UC-10 | `architecture-drift-rebaseline` | Compare current source code against the stored evidence-backed reverse-engineering baseline to identify stale architectural knowledge, undocumented routing changes, new integrations, removed behavior, or prior baseline errors. |
| `artifact-detailed-design` | Detailed Design | UC-07/08 | `design-to-implementation` | Produce a source-backed detailed design for exactly one registered design artifact at a time, preserving requirement/TDD traceability, current-source anchors, runtime/data provenance, compatibility, and explicit proposed-vs-existing boundaries. |
| `baseline-source-of-truth-maintenance` | Baseline Maintenance | UC-10 | `architecture-drift-rebaseline` | Safely maintain canonical reverse-engineering baseline after verified current-source changes. Enforces evidence lifecycle, promotion gates, supersession history, and removal of stale claims. |
| `claim-verification-and-promotion` | Evidence Gate | UC-01/03/06/09/11/12 | `many` | Verify candidate reverse-engineering claims against current source, actively search for counterexamples, narrow scope, and promote only defensible claims into canonical baseline memory. |
| `configuration-source-trace` | Source Analysis | UC-01/03/13 | `targeted-source-analysis` | Trace behavior-changing configuration from its external/source definition through loader, key/default/override precedence, runtime state, consumer branch, and resulting behavior; use to close configuration-origin unknowns. |
| `contract-impact-test-design` | Test Design | UC-04/06/07/08 | `patch-impact-to-tests / requirement-to-design` | Convert a source-backed patch or requirement impact analysis into contract-level test viewpoints, provenance-aware expected behavior, and spreadsheet-style Check ID matrices. | `design-artifact-decomposition` | Detailed Design | UC-07/08 | `design-to-implementation` | Decompose a verified technical design into a complete, source-traceable registry of implementation-relevant design artifacts and dependencies. Use after TDD verification and before detailed design or WBS generation. |
| `detailed-design-verification` | Design Gate | UC-07/08 | `design-to-implementation` | Independently verify one artifact detailed design against current source, verified TDD, artifact registry, requirement/gap traceability, provenance/exposure evidence, dependencies, compatibility constraints, and implementability. | `full-reverse-engineering` | Baseline | UC-01 | `full-reverse-engineering` | Orchestrate deep source-first reverse engineering with scope isolation, runtime/control-flow tracing, boundary-to-exposure closure, field/data provenance, configuration/persistence tracing, high-impact unknown closure, coverage audit, promotion gates, adversarial verification, and readiness certification. |
| `implementation-readiness-certification` | Readiness Gate | UC-07/08 | `design-to-implementation` | Certify whether a requirement-driven change is ready for implementation by verifying the complete traceability chain from requirement through gap analysis, TDD, design artifacts, verified detailed designs, WBS, and tests, with no unresolved source-resolvable high-impact gaps. |
| `incident-root-cause-analysis` | Incident | UC-11 | `incident-root-cause-analysis` | Analyze production or test incidents using logs and symptoms together with the reconstructed architecture. Use to localize failures, build timelines, test hypotheses, and distinguish evidence from speculation. |
| `integration-selection-analysis` | Source Analysis | UC-01/03/15 | `targeted-source-analysis` | Determine exactly how concrete clients/adapters/protocols/backends are selected, with mandatory counterexample search and promotion gates before routing rules enter canonical decision matrices. |
| `observability-traceability-analysis` | Observability | UC-12 | `observability-traceability-analysis` | Analyze whether a system has enough evidence to trace an operation across internal layers and external boundaries, identify troubleshooting blind spots, and design or review audit/log traceability without confusing logs with source-of-truth architecture. |
| `patch-impact-review` | Change Analysis | UC-04 | `patch-impact-to-tests` | Review a patch or Git diff against the evidence-backed current-system baseline, trace changed behavior through observable surfaces, runtime dependencies, integrations, and field/data provenance, identify compatibility/regression risks, and derive evidence-backed verification. | `persistence-schema-reverse-engineering` | Source Analysis | UC-01/03/16 | `targeted-source-analysis` | Reconstruct persistence architecture and database/data schema from current source, ORM mappings, SQL, migrations, DDL, schema bootstrap, upgrade scripts, and runtime repository wiring; distinguish code-known schema from external-only details. |
| `regression-test-design` | Test Design | UC-04/06/07/08 | `patch-impact-to-tests / requirement-to-design` | Generate a focused evidence-based regression test matrix from verified requirements, runtime behavior, patches, impact reviews, or proposed designs. Isolate requirement scope, derive provenance-aware test oracles, and avoid combinatorial explosion. |
| `requirement-compliance-review` | Requirement | UC-04/05/06 | `patch-impact-to-tests / requirement-to-design` | Compare a user/customer requirement against a patch's reconstructed implemented behavior and the current-system baseline. Use to determine whether development is correct, complete, over-scoped, or likely to regress unrelated behavior. |
| `resolve-high-impact-unknowns` | Evidence Gate | all source-backed workflows | `many` | Actively close HIGH/CRITICAL reverse-engineering unknowns by dispatching targeted source tracing, requiring search-exhaustion evidence before external blocking, and preventing premature baseline-readiness claims. |
| `resume-reverse-engineering` | Session/State | UC-01/02/03/04/06/07/08/09/10/11/12 | `many` | Rehydrate a fresh Copilot session from the existing 4.0 repository-backed reverse-engineering baseline and workflow state without restarting reverse engineering from scratch. |

| `run-engineering-workflow` | Orchestration | all workflow use cases | `all` | Execute declarative workflows as guarded state machines. | `runtime-flow-analysis` | Source Analysis | UC-01/03/04/06/11/12 | `many` | Trace a runtime operation end-to-end, record candidate claims, verify important behavior, and promote only claims that pass source verification, counterexample search, and scope checks. |
| `technical-design-proposal` | Design | UC-06/08 | `requirement-to-design` | Produce a reviewer-grade technical detailed design for a new feature or change using the evidence-backed current architecture as the design baseline. Use before implementation. |
| `technical-design-verification` | Design Gate | UC-07/08 | `design-to-implementation` | Verify a proposed technical design against the authoritative requirement, current repository, verified gap analysis, source-backed runtime/provenance/exposure evidence, compatibility constraints, and design traceability. | `wbs-generation` | Implementation Planning | UC-07/08 | `design-to-implementation` | Generate a traceable implementation Work Breakdown Structure from verified detailed-design artifacts, current source anchors, requirement/TDD traceability, dependencies, and verification obligations.
